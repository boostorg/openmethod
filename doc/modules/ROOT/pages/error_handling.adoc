
[#error_handling]

Errors can occur during `initialize`, or during method dispatch, if the method's
registry contains the `runtime_checks` policy. If the registry contains an
`error_handler` policy, its `error_handler::error` member function is called
with an error object, before terminating the program with a call to `abort`.
`default_registry` contains such a policy: `default_error_handler`. It wraps the
error object in a variant, and calls a handler via a `std::function`,
initialized to a function that prints a short description of the error to
`stderr`. The function can be changed, for example, to throw an exception:

[source,c++]
----
include::example$default_error_handler.cpp[tag=example]
----

Output:

[source,console]
----
spin
not implemented
spin
----

We can also replace the `error_handler` policy with our own. Since the handler
is part of the registry, this means overriding the default registry: the
listing opens by declaring `custom_registry` and naming it in
xref:reference:BOOST_OPENMETHOD_DEFAULT_REGISTRY.adoc[BOOST_OPENMETHOD_DEFAULT_REGISTRY],
then defines it further down, once the policy it is built from exists. See
xref:registries_and_policies.adoc[Registries and Policies] for that recipe.


[source,c++]
----
include::example$throw_error_handler.cpp[tag=example]
----

[source,console]
----
spin
not implemented
spin
----

Stock policy `throw_error_handler` does this for all the error types:

```c++
namespace boost::openmethod::policies {

struct throw_error_handler : error_handler {
    template<class Error>
    [[noreturn]] static auto error(const Error& error) -> void {
        throw error;
    }
};

} // namespace boost::openmethod::policies
```

## Runtime Checks

Only a registry that contains the cpp:runtime_checks[] policy diagnoses a
call that passes an object of an unregistered class, a call made before
`initialize`, or a cpp:final_virtual_ptr[] whose static and dynamic types
differ. Without the policy, nothing stands between the mistake and the
dispatch: the v-table pointer is read from a slot that `initialize` never
filled - a null one, or one past the end of the table - and the word found
there is called as a function. The call does not fail cleanly; where it
lands depends on what happens to be in memory at that address.

`default_registry` contains the policy only if
xref:reference:BOOST_OPENMETHOD_ENABLE_RUNTIME_CHECKS.adoc[BOOST_OPENMETHOD_ENABLE_RUNTIME_CHECKS]
is defined, which the CMake build does for debug builds. A program that
dispatches on objects it does not fully control - from a plugin, or built
from external input - should consider keeping the policy in release builds
too. The cost is a test of the initialized flag per call, and, with a
`type_hash` policy, one load and compare per virtual argument, against the
table of registered type ids.
