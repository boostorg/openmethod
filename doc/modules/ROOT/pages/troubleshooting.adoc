OpenMethod catches most mistakes at compile time. The rest surface at run time:
cpp:initialize[] reports inconsistencies in the registered classes, methods and
overriders, and a method call reports a combination of arguments that it cannot
dispatch. This page lists every error that the library reports, each under its
message, with a short example that produces it.

## Compilation errors

OpenMethod is a library that emulates a language feature. A mistake therefore
surfaces as a failed template instantiation, and the compiler reports it
together with the whole instantiation context, much of it inside the library.
Where the library can tell what went wrong, it says so in a `static_assert`.
Search the output for the message:

[cols="1,3"]
|===
| Compiler | Diagnostic

| gcc
| `static assertion failed: _message_`

| clang
| `static assertion failed due to requirement '...': _message_`

| MSVC
| `error C2338: static assertion failed: '_message_'`
|===

Read the first one. The errors that follow it are usually its consequences. In
particular, after an error in an overrider, gcc also reports
`BOOST_OPENMETHOD_OVERRIDE: the overrider does not match the method` or
`virtual_ptr category mismatch`, and after an error in a method, a
`static assertion failed` with no message. These add nothing to the first
error.

#### `BOOST_OPENMETHOD_OVERRIDE: cannot find '...' method that accepts the same arguments as the overrider`

*Example* - link:https://godbolt.org/clientstate/eNqNUltr2zAU%2FivCg5FQN1m6hzHPzcOoYXtoHJqyl7kYRVZsMVkSuiQNwfvtO%2FKlSTcXZj%2FY53yXc%2BGcAiKFpcIGEfp5CuxRUfiDJHe1CEL0FlwrKXw6vAhWuO7RgiYFs1K%2FgjcWW4%2BfAlbAZwEYx6JsFVdXnmqk06S1eMcE4a6gKGbSWE1xvcxEJs7pylplovl8KwGXupyVzFZuO2NyLhUVNbWVLDr0IjGrlGqNnGGiRAIaNgoTilpiFJ2ZXzwLKjti0QrmQadMIHj2TFuHOfrtk5MpukUF3WHHLQiaS9GaO4OiXvsKqY%2B5piWD6AiEXv6SiqIDTBIryRlh1ESRdsKymuakouSXWQ5mhGNj0D0T%2F5T5mqabxzxdJ6v75PFbejdRMNuOPYdo0nefK6tjL1mGyNgC5u52%2FH4aor1kxXTUJ09%2FJA8P3%2B%2BSSbeKcdu2o799kTSD9bBIaVAcoyy4zgK%2FukwETROi%2Fz0x%2BkyJe%2FvAXg5p5Mg8nXGq25THbj4uPniAs63pzlz0Vdqr8NC%2Boy8%2B3wTNE8RSWSaFZwfXMOgtWC8%2Bnc2xR9dYUL6p5EEAbYe5oRfFU2cHCI7CI1iXZlQC%2Fmzc7KCxGsKmeYL3D4lISjA%3D[Compiler Explorer^]

[source,c++]
----
include::example$troubleshooting/compile_fail_override_private_base.cpp[tag=content]
----

xref:reference:BOOST_OPENMETHOD_OVERRIDE.adoc[BOOST_OPENMETHOD_OVERRIDE] does
not take the method as an argument: it finds the method by overload resolution,
looking for a method of the same name that can be called with the overrider's
arguments. Here `Minus` derives from `Node` _privately_ - `class` makes the
inheritance private unless told otherwise - so a `virtual_ptr<Minus>` does not
convert to a `virtual_ptr<Node>`, and `postfix` cannot be called with one.

The other causes of the same message are:

* The method is not declared, or not before the overrider.

* The name is misspelled.

* The class of a virtual parameter does not derive from the class in the same
  position in the method, or does so ambiguously.

* The overrider has more, or fewer, parameters than the method.

* A virtual parameter is a reference in the method and a pointer in the
  overrider, or the other way around.

* The method takes a `virtual_` and the overrider a `virtual_ptr`. The
  overrider takes what the method takes, without the `virtual_`: `Plus&` for
  `virtual_<Node&>`.

* The method takes a smart `virtual_ptr`, such as cpp:shared_virtual_ptr[],
  and the overrider a plain `virtual_ptr`, or one over another kind of smart
  pointer. The opposite mistake has a message of its own:
  <<overrider_pointer_kind>>.

* A virtual parameter of the overrider is `const` where the method's is not.
  The opposite mistake has a message of its own: <<overrider_discards_const>>.

* A non-virtual parameter differs from the method's in a way that no
  conversion bridges. When a conversion does, the message is
  <<overrider_parameter_type>>.

* The method is in another namespace, and its arguments do not make it visible
  through argument-dependent lookup. See xref:namespaces.adoc[Namespaces].

When the overrider and the method differ only by their registry, the message
says so instead: <<registry_mismatch>>.

In the example, make the inheritance public: `class Minus : public Node`. A
`virtual_ptr<Minus>` then converts to a `virtual_ptr<Node>`, and overload
resolution finds `postfix`. For the other causes, make the overrider callable
the same way: declare the method first, correct the name, or match the
parameters to the method's.

[%autowidth,cols="1,3"]
|===
| Compiler | Diagnostic

| gcc
| `no matching function for call to ‘postfix(Plus&, std::ostream&)’`

| clang
| `no matching function for call to 'postfix'`

| MSVC
| `+'postfix': no matching overloaded function found+`
|===

The method and the overrider compile; the call does not. An object passed as a
virtual argument is converted to a cpp:virtual_ptr[], which needs the dynamic
type of the object. The default registry finds it with `typeid`, which yields
the dynamic type only for a polymorphic class, so `virtual_ptr` does not accept
`Node` or classes derived from it, and the call matches no overload. There is
no `static_assert` here, because the mistake is not in a declaration that the
library sees: it is the absence of a conversion. For the same reason,
`virtual_ptr<Node> p(plus)` reports that no constructor matches.

Make the root of the hierarchy polymorphic by giving it a virtual destructor -
which it needs anyway, if objects are ever deleted through a pointer to it.
`typeid` then yields the dynamic type of a `Node`, and the object converts to a
`virtual_ptr`.

*Fix*

[source,c++]
----
include::example$troubleshooting/fix_call_non_polymorphic.cpp[tag=content]
----

Where the classes must stay non-polymorphic, there are alternatives.
cpp:inplace_vptr_base[] gives a class a v-table pointer of its own, and a
custom RTTI policy can find the dynamic type of non-polymorphic classes: see
xref:custom_rtti.adoc[Custom RTTI].

Where the caller knows the exact class of the object, cpp:final_virtual_ptr[]
makes a `virtual_ptr` without looking for the dynamic type. It takes the static
type of its argument instead, so it works with any registered class,
polymorphic or not:

[source,c++]
----
Plus plus;
postfix(final_virtual_ptr(plus), std::cout);
----

Nothing checks that the static type is the dynamic type: with a non-polymorphic
class, OpenMethod has no way to find out, even with runtime checks enabled.
Passed a `Node&` that refers to a `Plus`, `final_virtual_ptr` makes a
`virtual_ptr` to a `Node`, and the call dispatches on `Node`.

#### `+named_static_rtti requires __PRETTY_FUNCTION__ or __FUNCSIG__+`

cpp:named_static_rtti[] derives class names from the predefined function name
of GCC, Clang or MSVC, and the compiler provides neither.

Use cpp:static_rtti[] instead, if the program is a single module. The names
are what lets `named_static_rtti` merge the copies of a class that come from

ids differ from one module to the next. A program that shares classes across
shared libraries needs cpp:std_rtti[], or a custom RTTI policy: see
xref:custom_rtti.adoc[Custom RTTI].

## Runtime errors

Errors detected at run time are passed to the registry's
cpp:error_handler[] policy. The one in cpp:default_registry[] writes the
message to `stderr`, then the program is terminated with `abort`.
xref:error_handling.adoc[Error Handling] explains how to change that, for
example to throw an exception. Each section below names the error type that a
custom handler receives.

cpp:initialize[] always checks the classes, methods and overriders it is given,
and a call that finds no overrider, or several ambiguous ones, is always
reported. The other checks made during a call - for an unregistered class, a
call before `initialize`, a misused cpp:final_virtual_ptr[] - are made only if
the registry contains the cpp:runtime_checks[] policy. `default_registry`
contains it if
xref:reference:BOOST_OPENMETHOD_ENABLE_RUNTIME_CHECKS.adoc[BOOST_OPENMETHOD_ENABLE_RUNTIME_CHECKS]
is defined, which is recommended in debug builds.

### Hash tables

The `type_hash` policy maps type ids to the indexes of the v-tables. Its
`initialize` searches for a function that does that for the registered classes,
and reports an error if it cannot find one. Each policy has its own:

[cols="2,2"]
|===
| Message | Policy

| `could not find hash factors after _N_ attempts using up to _M_ buckets`
| cpp:fast_perfect_hash[], the default

| `could not place _N_ type ids after trying _M_ multipliers`
| cpp:minimal_perfect_hash[]

| `+could not place N type ids in a table of up to 2^B slots+`
| cpp:two_level_hash[]

| `the smallest bit cover of _N_ type ids is _B_ bits wide, more than the _M_ allowed`
| cpp:minimal_cover_hash[]
|===

With the default limits, the first three are unlikely with ordinary type ids,
and cannot be provoked by a small program. The last two policies take their
limits as template arguments, so it takes a registry configured to fail:
